# 2.4G LED 控制验证完整记录

- 首轮验证：2026-10-26
- 保持/休眠/保活复测：2026-10-27
- 设备：LEOBOG Hi86 键盘 + `3554:FA09` 接收器（CX 2.4G Wireless Receiver）
- 目的：验证 2.4G 无线模式能否控制键盘 LED，以及能否当「常亮状态牌」用

> **给后续接手的智能体**：先读这一节「结论速览」和「保持与休眠」两节，再看协议细节。
> 2026-10-26 那一版记录的保持结论是错的（当时误信了另一把键盘的源码注释），已在 10-27 用实测推翻并改正。

## 结论速览

| 项目 | 结果 |
|---|---|
| 2.4G 能否控制 LED | ✅ 能 |
| 单键精确控制（亮/灭/颜色） | ✅ 能，键 1/5/9 实测亮绿 |
| 全键盘 126 LED 控制 | ✅ 能 |
| 是否需要管理员 | ❌ 标准权限即可 |
| 单帧能保持多久（不补帧） | **约 60 秒**，之后键盘空闲关灯；**1 分 10 秒左右链路断开** |
| 补帧能否维持常亮 | ✅ 能。30 秒间隔跑 6 分钟、45 秒间隔跑 6 分钟，链路全程正常 |
| 补帧代价 | 每次发送灯会黑约 **1 秒**再亮（无法避免） |
| 休眠后发帧能否唤醒 | ❌ 不能。断链后发送直接失败，只有物理按键能唤醒 |
| 补帧时打字 | ❌ **每一帧都会丢键**。实测 15 帧 / 15 次出错（100%），不补帧时 0 次 |
| 打字时灯会不会灭 | ❌ 不会。按键会重置空闲计时，连续打字 3 分钟灯全程亮 |
| 那什么时候需要补帧 | 只在**手停下来**之后（人或离开键盘时）。打字期间完全不用补，也不该补 |
| 插 USB 线 | ❌ 键盘切有线模式，2.4G 写入报成功但**不生效** |
| 高频补帧是否影响打字 | 影响。1.5s / 4s 间隔都会明显滞涩、按键重复 |
| 推荐策略 | 状态变化时发 1 帧；要 2.4G 常亮就 45 秒补一帧，接受每 45 秒闪一下；有人打字时暂停补帧；插线就改走有线协议 |

## 保持与休眠（2026-10-27 实测，这是最重要的部分）

三组实验，都不碰键盘：

| 实验 | 脚本 | 结果 |
|---|---|---|
| 不补帧，只发 1 帧 | `hold_test.py` | 约 60 秒灯自己灭；链路在 1–2 分钟之间变成「无回包」 |
| 同样不补帧，第二轮 | `hold_test.py` | 1 分 00 秒链路正常；2 分 00 秒链路无回包 |
| 每 30 秒补一帧，跑 6 分钟 | `keepalive_test.py` | 12 帧全部发送成功，**链路每 15 秒查一次，全程「正常」** |

### 三件事必须分清

1. **灯灭 ≠ 灯效回落。** 键盘没有把我们设的颜色换回内置灯效，它是关灯了。
2. **灯灭 ≠ 立刻断链。** 灯先灭（约 60 秒），链路可能还活着几十秒，然后才彻底断开。
3. **按任意键会唤醒，且会恢复上次那一帧颜色。** 所以观测时按回车会「把灯点亮」，
   让人误以为灯没灭过。这是 10-26 那轮得出「保持 ≥7 分钟」错误结论的原因——
   当时每隔一会儿按一次回车，一直在替键盘续命。

### 补帧的效果（关键数据）

`keepalive_20261027_091718.txt`，30 秒间隔，6 分钟：

- 第 1 帧 09:17:22 发出，之后 2..12 帧每 30 秒一帧，全部发送成功。
- 链路状态每 15 秒查一次，从 15 秒到 5 分 45 秒，**一次「无回包」都没有**。
- 观察（用户实看）：约第 4 帧（1 分 30 秒左右）灯灭过，隔几秒自己亮回来；
  从第 5 帧起，**每次补帧都会让灯黑约 1 秒，然后恢复**。

推论：

- 补帧确实能压住键盘的空闲休眠，30 秒间隔够用。
- 每次补帧的黑屏是写入本身引起的（整帧 378 字节、27 包），不是我们发错了。
- 所以「2.4G 常亮」= 每 30 秒闪 1 秒，约 3% 时间不可读。

### 第二轮：45 秒间隔（`keepalive_20261027_093658.txt`）

- 45 秒间隔，6 分钟共 8 帧，全部发送成功。
- 链路每 15 秒查一次，从 15 秒到 5 分 45 秒**全程正常**。
- 观察：每帧仍然黑约 1 秒，但频率从每 30 秒一次降到每 45 秒一次。

**结论：45 秒比 30 秒好，同样能压住休眠，闪烁少三分之一。**
再往上加（60 秒）没有余地——不补帧时 60 秒就关灯。

### 第三轮：休眠与唤醒（`wake_test_20261027_094327.txt`）

不补帧、不碰键盘，程序每 5 秒查一次链路：

| 时刻 | 链路 |
|---|---|
| 0 – 1 分 05 秒 | 正常 |
| 1 分 10 秒 | **无回包（已断链）** |

断链后连发 3 帧颜色：

```
第 1 帧 发送失败   链路：回了包但键盘未连
第 2 帧 发送失败   链路：回了包但键盘未连
第 3 帧 发送失败   链路：回了包但键盘未连
```

按一下键盘之后，链路恢复「正常」。

**结论：颜色帧叫不醒键盘，只有物理按键能唤醒。**

注意两种链路状态要分清，对守护程序有用：

| GetDongleStatus 回包 | 含义 |
|---|---|
| 有回包，byte4 非 0 | 键盘已连 |
| 有回包，byte4 = 0 | 接收器活着，键盘不在（睡着/走远） |
| 无回包 | 接收器自己也没响应 |

另外：唤醒后灯会不会恢复，取决于**睡之前有没有成功写入过帧**。
第三轮从头到尾没发过帧，所以按下按键后灯仍然不亮，这不是故障。

### 第四轮：补帧时打字（菜单第 5 项，30 秒间隔，120 秒）

用户实测：打字过程基本流畅，没有明显延迟。

但**在脚本输出文本、发送收尾全灭帧的那一刻，出现了 10 多个连续重复字符**。

解释：发帧占满 2.4G 链路的那 0.25 秒里，键盘的上报报文可能丢失。
**如果丢的是按键抬起（key-up），系统就认为那键一直按着，于是开始自动重复。**

这同时解释了 10-26 那轮的「1.5s / 4s 重发导致按键重复」——不是带宽不够，
是**丢事件**。间隔再长也会丢，只是概率低。

**结论：补帧和打字不能同时进行。** 守护程序里应当在检测到输入活动时暂停补帧。

### 第六轮：丢键到底多严重（`keydrop_20261027_101032.txt`）

两段对照，同一个键盘、同一段文字：

| 段 | 时长 | 补帧 | 出错次数 |
|---|---|---|---|
| A 段（对照） | 60 秒 | 不发 | **0 次** |
| B 段（测试） | 120 秒 | 每 8 秒一帧，共 15 帧 | **15 次** |

**15 帧 = 15 次出错，几乎每帧必丢一次。**

A 段 0 次说明键盘本身不丢键，问题 100% 来自补帧。

**结论：不是「概率低可以忍」，是「每帧必错」。**
只要用户在打字，就不能补帧，没有折中余地。

### 第七轮：打字能不能维持灯亮（`typing_hold_test.py`，3 分钟）

发 1 帧后，用户连续打字 3 分钟，**程序这期间一帧都不发**，只打印时间。

结果：**全程灯亮，没有灭。**

**结论：键盘的空闲关灯计时是「按键重置」的。人在打字时灯不会灭。**

所以最终规则可以写得很干净：

```
打字中               → 不发帧（灯靠按键自己维持，不闪、不丢键）
距上次按键 >= 20 秒  → 发一帧（此时人不打字，丢键风险最小）
距上次发帧 >= 45 秒  → 才允许再发（限流，避免发太密）
```

灯在 60 秒后关，20 秒补第一帧，有 40 秒余量。

### 第五轮：插 USB 线（`hold_test_20261027_094703.txt` + 设备列表）

插上线后跑单帧测试：脚本报「已发送 1 帧」，但**灯不亮**。
`GetDongleStatus` 仍然回「正常」。

查系统设备，插线后多出一个同 VID/PID 的设备树：

```
USB\VID_3554&PID_FA09\7&338C545E&0&0000   ← 接收器
USB\VID_3554&PID_FA09\6&222FDAA7&0&2      ← 插线后多出来的有线键盘
```

**结论：插线后键盘走有线通道，2.4G 写入会被接收器 ACK，但键盘不执行。**

这是一个危险的假成功：
- 接收器照常回 ACK，脚本以为写成功了
- 灯没有任何反应
- 排查时很容易以为是协议或索引写错

**所以插线场景必须走有线协议（`src/traffic_light/frame.py` 的 520 字节特征报告），
不能用 2.4G 这条路径。**

## 协议关键事实

### 通道
- 设备：`3554:FA09` COL01 集合
- 用法页/用法：`0xFF02 / 0x0002`
- 输出报告 ID：`0x13`，长度 20 字节（1 字节报告 ID + 19 字节包）
- 接收器会主动推送 `ActivelyReport`（cmd 10），读回包时必须跳过
- 设备路径**不要写死**：该接收器换过至少 4 个实例 ID（`8&1D8973AD`、`9&18A0EE90`、`8&64DCA15`、`9&30647AD5`），换 USB 口就变。
  用 `dongle_led.py` 的 `enumerate_dongle_paths()` + `open_dongle()`：现场枚举所有 `vid_3554&pid_fa09` 接口，逐个打开握手，第一个应答的就是 COL01。

### 19 字节包布局
```
byte  0      命令号
byte  1      包总数 & 0x7F
byte  2      包序号 & 0x7F
byte  3      (数据长度 & 0x0F) | (board << 4)
byte 4..17   最多 14 字节载荷
byte 18      CRC = (19 + sum(byte 0..16)) & 0xFF
```

### 颜色缓冲（378 字节）
- 27 包逐包发送，每包必须等接收器回 ACK
- ACK 判定：回包 `byte0 == cmd` 且 `byte1 >> 7 == 0`
- **布局为 3 平面，不是扁平 RGB 三元组**（上游仓库文档写错，源码 `R87ProDongle.cpp` 正确）：
  ```
  R 平面: [0..125]      → buffer[led] = R
  G 平面: [126..251]    → buffer[126+led] = G
  B 平面: [252..377]    → buffer[252+led] = B
  ```

### 命令号
| 号 | 说明 |
|---|---|
| 2  | SetLedColors |
| 5  | GetPassword（回包 [8..9] 为型号，Hi86 = 0x018D） |
| 7  | GetDongleStatus（回包 byte4 非 0 = 键盘已连；无回包 = 已断链/休眠） |
| 10 | ActivelyReport（接收器 → 主机，忽略） |
| 66 | GetLedColors（**实测接收器不回包，读不回来**） |

### 帧耗时
一帧 378 字节 / 27 包，约 **0.25 秒** 发完（连接状态下）。

## 七个曾经踩过的坑

### 坑 1：`WriteFile` 返回 True 不等于接收器收到
`kernel32.WriteFile` 只代表 20 字节写进了 HID 驱动，不代表接收器收到，更不代表 ACK。
必须逐包读 ACK，否则「发送成功」是假象，灯不会亮。

旧脚本 `test_keys.py` 就是这个错误。

### 坑 2：颜色缓冲布局搞错
上游文档说「扁平 RGB 三元组」，实际是**三平面**。
按扁平布局发，灯会亮在完全无关的键上，或者根本不亮。

### 坑 3：读回包阻塞
直接用阻塞 `ReadFile` 轮询，接收器没数据时 `ReadFile` 永久阻塞，整个 27 包流程卡死。

正确做法：用 `FILE_FLAG_OVERLAPPED` 打开设备，配合 `WaitForSingleObject` + `CancelIo` 做硬超时。
`dongle_led.py` 的 `Dongle` 类已实现。

### 坑 4：键盘空闲会关灯，然后休眠
约 60 秒没有按键就关灯；再往后链路断开，`GetDongleStatus` 直接**无回包**（不是 byte4 = 0）。
按一下键盘任意键唤醒，醒来后会把我们上次设的那一帧恢复出来。

**推论**：任何「让人看、不让人碰」的展示都必须补帧，否则一分钟后就是一盏黑键盘。

### 坑 5：信了另一把键盘的源码注释，得出「必须 1.5–4 秒重发」
`myxk1792/openrgb-rk-r87pro` 的注释针对 R87 Pro，说颜色帧几秒就失效、要周期重发。
对 Hi86 **不成立**：实测单帧保持约 60 秒，不是几秒。

更糟的是照这个结论做，每 1.5 秒重发一次，导致打字非常滞涩、按键重复——
**卡顿是我们自己造成的**，不是 2.4G 链路本来就慢。

### 坑 6：插线后 2.4G 写入「成功」但无效
插上 USB 线，键盘会切到有线模式（系统里出现第二个 `3554:FA09` 设备）。
此时往接收器发颜色帧：接收器照样逐包 ACK，脚本报成功，**灯一动不动**。

判定方法：插线后 `GetDongleStatus` 仍回「正常」，但发帧后灯不亮。
这时要改走有线路径，不要怀疑协议或 LED 索引。

### 坑 7：补帧会丢按键事件
发帧占满链路的那 0.25 秒里，键盘的输入报文可能丢，尤其是**按键抬起**。
丢了 key-up，系统就认为键一直按着，于是自动重复，打出一串相同字符。

实测（`keydrop_20261027_101032.txt`）：每 8 秒补一帧，120 秒共 15 帧，**15 次出错**；
同样打字 60 秒不发帧，**0 次**。

所以这不是偶发，是**每帧必错**。看到打字突然出现一串重复字符，
先怀疑是不是刚补过帧。

## 干扰数据（2026-10-26 实测，结论仍然有效）

| 重发间隔 | 链路占用率 | 打字手感 |
|---|---|---|
| 1.5s | ~17% | 非常滞涩，明显延迟，Shift 切输入法无响应，按键重复 |
| 4s   | ~6%  | 仍滞涩，有延迟，按键重复现象仍在 |
| 30s  | ~0.8% | 没测打字手感（演示场景无人打字），但链路 6 分钟无异常 |

结论：**高频保活不可用于输入场景**。30 秒级补帧是另一个量级，可以接受，
但要在「用户可能正在打字」的场景下实测一次再定。

## 后续接进守护程序时的落点

- `src/traffic_light/profiles.py` 的 `Hi86Profile` 接缝：需要实现 2.4G 写入路径
- `src/traffic_light/keyboard.py::_notify_wired_needed`：现在的提示语基于错误结论，要改
- 策略建议：
  - **有线优先**：走 520 字节特征报告路径（`frame.py` 已有），无闪烁、无休眠、不丢键
  - **2.4G 常亮**：灯态变化立刻发 1 帧；之后每 45 秒补 1 帧。接受每 45 秒约 1 秒黑
  - **2.4G 只看一眼**：只在状态变化时发，灯一分钟后自己灭。适合「人就在旁边、随时会碰键盘」的场景
  - **打字时绝对不能补帧**：实测每帧必丢一次按键事件。而且不需要补——
    按键本身会重置空闲计时，人在打字时灯不会灭（实测连续打字 3 分钟全程亮）。
    可行规则：
    ```
    if 距上次按键 >= 20 秒 and 距上次发帧 >= 45 秒:  发一帧
    ```
    即「人在打字就不补，人停下来才补」。灯 60 秒后关，20 秒补第一帧，有 40 秒余量。
    具体阈值要接进守护后实测
  - **检测到插线就切有线路径**：2.4G 写入此时会 ACK 但不生效，必须换路径
  - 不能用帧唤醒键盘：休眠后只能靠物理按键，所以「平时不补帧、需要时点火」做不到
- 一个可优化点：补帧时只发送**变化了的 LED**？协议是整帧 378 字节，似乎不支持局部更新，未验证。
